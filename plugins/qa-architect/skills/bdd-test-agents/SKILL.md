# Playwright Test Agents for BDD suites

Playwright ships three agent definitions — **planner** (explores the app, writes a Markdown plan),
**generator** (turns a plan item into a test by driving the browser live) and **healer** (runs,
debugs and repairs failing tests). They assume plain `*.spec.ts` files.

A playwright-bdd suite breaks that assumption: its specs are **generated by `bddgen`** into
`.features-gen/` and overwritten on every run. An agent that edits a spec there loses its work, and
one that writes a new raw spec bypasses Gherkin, the step library and the Page Object Model. This
skill keeps the agents but redirects every artifact to where it belongs:

| Agent output | Where it goes in a BDD suite |
|---|---|
| Plan (Markdown) | `specs/<area>.md` — reviewed by a human, then translated to `features/<area>.feature` |
| Generated interactions & selectors | New `GeorgePage`-style Page Object methods (selectors live **only** there) |
| Generated assertions | `Then` step definitions calling Page Object methods |
| Healer fixes | The Page Object / step file the stack trace points at — never `.features-gen/` |

## Step 0 — Load calibration and detect the suite

1. Read `.qa/project.md`, `.qa/preferences.md` and the suite's `CLAUDE.md` (layer order as in the
   `automate-tests` skill). Respect environment constraints — e.g. George FAT: `workers: 1`, one
   shared account, 120s timeout, never "optimize" those away.
2. Confirm it is a playwright-bdd suite: `playwright-bdd` in `package.json`, `defineBddConfig` in
   `playwright.config.ts`. If not, use the `automate-tests` skill instead.
3. Inventory the existing step library — this is what you reuse first:
   ```bash
   npx bddgen export          # every step pattern the suite already defines
   ```
4. Note the tag vocabulary already in `features/` (`@smoke`, `@negative`, `@edge-case`, …) and
   reuse it; don't invent near-duplicates.

## Step 1 — One-time setup (seed + agent definitions)

The agents' MCP server starts every session by running a **seed test** found through a Playwright
config. A BDD config's `testDir` is bddgen output, so the suite needs a small agents config:

- `playwright.agents.config.ts` — spreads the main config, sets `testDir: './e2e/agents'`.
- `e2e/agents/seed.spec.ts` — logs in through the suite's existing auth fixture and lands on the
  start page. Nothing else.

`e2e/george-search` already has both. For another suite, create them, then from the suite dir:

```bash
npx playwright test -c playwright.agents.config.ts --list      # seed must be listed
npx playwright init-agents --loop claude -c playwright.agents.config.ts --project chromium
```

`init-agents` writes `.claude/agents/playwright-test-{planner,generator,healer}.md`, a `specs/`
dir and an `.mcp.json` registering the `playwright-test` MCP server (`npx playwright
run-test-mcp-server`). Re-run it after every Playwright upgrade — the definitions are versioned
with Playwright. Tell the user Claude Code must be restarted in that directory to pick up the new
agents and MCP server; don't continue until they are available.

## Step 2 — Plan (planner agent) → human gate

Dispatch `playwright-test-planner` with the area to cover and the seed path. It saves
`specs/<area>.md`.

Then **stop and show the user the plan** as a compact table (one row per scenario, emoji for type:
✅ happy · ❌ negative · ⚠️ edge · 🔒 security), marking which scenarios are already covered by an
existing `.feature`. Ask which to keep. Don't generate anything the user hasn't approved.

## Step 3 — Translate the approved plan into Gherkin

Write or extend `features/<area>.feature`:

- **Reuse existing step phrasings verbatim** from the `bddgen export` list wherever the meaning
  matches — a scenario made entirely of existing steps needs no new code at all.
- One behaviour per scenario; `Scenario Outline` + `Examples` for data variations.
- Tag every scenario from the existing vocabulary.
- Keep steps declarative ("the user searches for {string}"), never UI-mechanical ("clicks the
  third button").

Run `npx bddgen` — it lists every step that has no definition yet (playwright-bdd 9 also checks
step arity strictly). That list is the generator's work queue.

## Step 4 — Generate the missing steps (generator agent) → refactor into POM + steps

For each scenario that uses missing steps, dispatch `playwright-test-generator` with the scenario
as the plan item and the seed file. It drives the browser and writes a scratch spec under
`e2e/agents/` with selectors and assertions it **verified live**.

Then refactor that scratch spec — this is the important part:

1. Every selector / interaction → a named method on the Page Object (`george.page.ts`). Prefer
   `getByRole` / `getByLabel` / `getByPlaceholder`; keep any unavoidable hashed CSS-module class
   in exactly one place.
2. Every missing step → a definition in `e2e/steps/*.steps.ts` built with the suite's `Given/When/
   Then` from `createBdd(test)`, calling only Page Object methods. **No selectors in steps.**
3. Delete the scratch spec. Agent output never stays in `e2e/agents/` except the seed.

## Step 5 — Run and heal (healer agent, redirected)

```bash
npx bddgen && npx playwright test --grep @<area-tag> --project=chromium
```

On failures, dispatch `playwright-test-healer`, telling it explicitly:

- `.features-gen/` is generated — read it to locate the failure, but apply every fix to the Page
  Object or step definition the stack trace points into, then re-run `bddgen`.
- Never weaken an assertion or loosen an expected value to get green. If the app is wrong, it's a
  **product bug**: stop, report it, and leave the test red (or tag the scenario `@fixme` with the
  reason, if the user agrees).
- For a broken selector the healer can't resolve, fall back to the repo's deterministic healer:
  `npm run self-heal -- --ai --dry-run -- npx playwright test --grep @<tag>` and review its diff.

Healer fixes are proposals: show the diff and get approval before the final run.

## Step 6 — Report

Compact table, one row per scenario: status (🟢 pass · 🔴 product bug · 🟡 fixme), feature file,
new steps added, Page Object methods added/changed. List anything the user still needs to decide.
Offer to commit; don't push without being asked.

## Guardrails

- The agents and the healer run in a real browser against a real environment. On shared or
  production-like environments (George FAT), confirm before any flow that mutates data.
- `workers: 1` and other documented environment constraints stay untouched.
- Selectors live only in the Page Object; steps call methods; features stay declarative.
- `.features-gen/` and scratch specs are never committed.
